The Idea

Most "live data" portfolio widgets stop at generic. This one is personal.

Take a visitor's own location — estimated, not tracked — and show them something genuinely live and specific to them: what's flying overhead, right now, within 25 miles.

The brief was simple: build a small piece of live-data functionality that's worth doing carefully. It touches geolocation without consent fatigue, a real-time public API with real rate limits, and a visual that communicates uncertainty rather than overstating precision. Three things that are easy to get wrong.

1
Consent first, always

Nothing happens — no IP lookup, no API call — until the visitor explicitly clicks "Show nearby flights." The gate explains in plain language that location is estimated from IP (typically city-level, not an exact address), that the lookup goes straight from the browser to a third-party service, and that nothing is stored. A "Stop tracking" control lets anyone back out at any point. A manual coordinates field lets visitors skip IP lookup entirely.

2
IP → approximate coordinates

On consent, the browser calls ipapi.co/json/ for a {latitude, longitude, city} estimate, falling back to ipwho.is if the first call fails. Both are free, keyless, and called directly from the client — no server in the loop.

3
Coordinates → bounding box

A 25-mile radius is converted to a lat/lon bounding box (miles / 69 for latitude, adjusted by cos(latitude) for longitude) and sent to OpenSky Network's free states/all endpoint — which returns every aircraft currently inside that box from its global ADS-B feed.

4
Filter and project

Grounded aircraft are dropped. Each remaining aircraft's great-circle distance and bearing from the visitor's estimated position is computed (haversine + initial bearing formula). Anything outside the true 25-mile circle is discarded — the bounding box is rectangular, so this second pass keeps the radius honest.

5
Render as a radar scope, not a map

Aircraft are plotted by bearing and distance on an SVG scope with range rings at 5/10/15/20/25 miles, color-coded by altitude band, with a rotating sweep animation. An IP-based estimate is genuinely fuzzy — a real map with a pin implies more precision than the data has. A radar scope tells the truth about what's known (direction and rough distance) without pretending to know where someone actually is.

6
Poll, don't hammer

The OpenSky request repeats every 30 seconds while the tab is visible, paused via the Page Visibility API when it isn't — well clear of the anonymous tier's rate limit. A manual refresh button has its own 15-second cooldown.

Design Decisions

Four things worth calling out explicitly.

🔒
Opt-in over opt-out

The default state does nothing. Location data, even coarse IP-based location, shouldn't be collected silently on page load. This was non-negotiable from the first version.

📡
Honesty about precision

The consent copy and the radar-scope visual both work to avoid implying the widget knows more than it does. IP geolocation is a city-level estimate; VPNs and corporate networks shift it further still.

🗑️
No backend, no persistence

Every value lives in memory for the current page view. Closing the tab clears everything. This also keeps the widget trivially embeddable: copy four blocks of markup into an existing page and it works.

✈️
A logo from the same system

The consent screen's mark is a small plane orbiting a ring, animated in CSS. It's a miniature of the main radar scope — brand and feature are visually the same idea at two sizes, not an unrelated glyph.

Why a radar scope instead of a map

A street map with a location pin communicates false precision — it implies the system knows exactly where you are. A radar scope is truthful: it shows direction and rough distance relative to an estimated centre. Visitors understand they're getting an approximation. The visual and the data tell the same story.

Lessons Learned

Two bugs worth writing down.

Lesson 01
An absolutely positioned element can only fill a parent that has size from something else

The most instructive bug wasn't the API integration — it was layout. The consent screen used position: absolute; inset: 0 to overlay on top of the initially hidden main interface. The container had no explicit width or height, and every one of its children was either absolutely positioned or hidden, meaning nothing remained in normal document flow to give the container any size to fill. The result: a container that collapsed to zero height, then zero width, rendering as a blank panel and then a single vertical sliver before the actual cause was found. Fix: give the container an explicit width and min-height. Easy to miss any time you build a consent gate, modal, or "cover the whole card until X happens" pattern.

Lesson 02
AI chat artifact previews sandbox outbound fetch — that's correct behaviour, not a bug

Testing inside an AI chat tool's artifact preview isn't the same as testing in a real browser tab. Artifact previews commonly sandbox outbound fetch() calls via CSP — which is correct and important for security. That means "the geolocation lookup is failing" can mean either a real bug or just the preview environment doing its job. Always confirm against the actual hosted file before chasing a phantom bug in the API integration.

Possible Next Steps

Where it could go next.

  • Cache the visitor's IP-based location for the session so a manual refresh doesn't redo the geolocation lookup.
  • Add a unit toggle (imperial / metric) for an international audience.
  • Surface aircraft type and operator — OpenSky's metadata endpoints support this, at the cost of one extra request per aircraft.
  • Swap in the Flightradar24 API for richer flight metadata if the project ever needs commercial-grade reliability and is willing to pay for it.
